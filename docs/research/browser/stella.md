# Rocketnet browser client: independent research

Research snapshot: 2026-10-13 America/New_York (2026-10-14 UTC). Source checkout: `11a39bfeeeaa491a11caa7ba277c43e7d73126d2`. No implementation, compilation, server, test, or benchmark was run. This is a design comparison, not performance or security certification. External sources were opened on the snapshot date; moving web pages are not pinned releases. **SOURCED** denotes inspected evidence; **ESTIMATED** denotes arithmetic or a planning range; **OPINION** denotes a proposed choice. **UNVERIFIED** is an unresolved factual claim, not a zero or a negative result. References [R1–R8] are private local source at the exact head; [S1–S60] are the external source register in section 9.

**OPINION:** Start with WebTransport HTTP/3 datagrams through a native gateway, preserve Rocketnet's inner encryption, and ship a bounded WebSocket fallback. Make WebRTC unordered, zero-retransmit data channels the challenger, especially for older Apple devices and networks where TURN helps. Prefer a single-threaded WASM port of the existing client over a second wire implementation, conditional on the first portability and size experiments. Do not choose a QUIC library merely because it implements QUIC: browser WebTransport also needs the matching HTTP/3 session protocol. [R1–R5; S1–S10]

## 1 Transports

The following are **SOURCED** protocol properties; latency/CPU outcomes remain **UNVERIFIED** until the proposed harness runs. Browser code cannot send Rocketnet's raw UDP directly through these APIs. Emscripten's socket emulation does not remove this restriction. [S1, S4, S6, S25]

| Candidate | Delivery and size | Congestion and 10–60 Hz implications | Setup, reach, latency |
|---|---|---|---|
| WebTransport over HTTP/3 | Unordered, unreliable datagrams; reliable ordered streams independently. Read `datagrams.maxDatagramSize`; no universal 1232-byte application allowance. QUIC DATAGRAM cannot be fragmented by QUIC. | QUIC congestion control applies to datagrams and streams; no raw-UDP bypass. Bound queued age and bytes; fresh snapshots may be discarded before enqueue. Bulk streams consume shared connection capacity. | TLS/QUIC plus HTTP/3 CONNECT/session readiness; optional Retry adds work. Outbound UDP, usually 443. It must not silently satisfy the H3 datagram success gate. [S1, S10] |

**ESTIMATED setup model, not a browser timing claim:** Let R be client-to-transport-endpoint RTT, G the gateway/server RTT, and Q scheduling delay. An ideal fresh H3 outer setup might take roughly 1–2R before application readiness, or more with Retry/settings waits. Then unchanged Rocketnet adds approximately 3(R+G)+Q. WebSocket's ideal cold TCP+TLS1.3+upgrade path is roughly 3R before those inner exchanges. WebRTC's critical path depends on which signaling, STUN/TURN, ICE, DTLS and SCTP steps overlap; planning 3–8R is a deliberately broad hypothesis, not a limit. Measure each milestone separately. A STUN transaction costs one request/response in the no-loss case; authenticated TURN may require a challenge/retry, then permission/channel work. ICE checks can run in parallel and can also time out. Crypto CPU and wakeups cannot be inferred from RTT counts. [R1; S29–S35]

**OPINION WebSocket mitigation set:** Set TCP_NODELAY at the native endpoint; verify packet capture because the browser has no corresponding control. Disable compression for already encrypted packets. Keep messages small; separate bulk asset downloads from gameplay; bound `bufferedAmount` and application queue age; coalesce unsent replaceable state before encryption; include game timestamps; drop stale snapshots on receipt; reconnect when a queue is irrecoverably old. Prioritize control before bulk, avoid giant frame serialization, and measure server flush cadence. Separate WebSockets isolate connection-level blocking but add sockets and congestion competition and cannot cure loss within a given connection. Never omit a reliable message merely because it is old. None of these removes TCP head-of-line blocking. [S6, S35; R2]

**SOURCED certificate constraint:** Ordinary WebTransport uses HTTPS certificate validation. `serverCertificateHashes` supplies certificate hashes rather than a general trust-store override; MDN specifies SHA-256, short-lived X.509v3 certificates valid for less than two weeks, ECDSA P-256 as the interoperable default, and no RSA. Current compatibility data lists hashes from Chrome 100, Firefox 125, Safari 26.4. Deliver hashes through authenticated backend configuration, rotate overlapping certificates, and test clock skew and expiry. Prefer normal publicly trusted names/certificates for production. Hash authentication is not an excuse to accept arbitrary certificates. [S1, S11, S41]

**OPINION alternatives:** Direct native QUIC is useful for native clients but is not a browser raw-QUIC API. A WebSocket control plane plus WT/RTC datagrams is plausible; avoid allocating two Rocketnet sessions for one player. Media-over-QUIC's subscription/object model may serve spectators and replays, but does not solve browser API reach or replace Rocketnet packet semantics. WebRTC relaying is a server topology, not another browser transport. WebSocket emulation of UDP is a reliable tunnel and must be advertised accordingly. Browser extensions/plugins are outside scope. [S1, S25, S36]

**OPINION topology A, initial recommendation:** One authenticated browser transport session maps to one connected UDP socket/source port toward the chosen game server. The gateway forwards complete inner wire packets, retaining the socket for the connection lifetime. Two browser clients sharing a gateway IP still need distinct source ports for the same server; one shared socket without a revised native demultiplexer merges identity incorrectly. Normalize the browser client's virtual peer address to the server IP/port in the signed token. Gateway destination selection must match an allowlisted signed server route; never turn it into an arbitrary UDP proxy. [R1, R4]

**ESTIMATED capacity model:** A source IP has at most 65,536 UDP port values before reservations and OS policy. Practical usable ports P are smaller: capacity per source-IP/server pair is at most P, not an arbitrary million clients. For C sessions choose at least ceil(C/P) gateway source IPs, then provision additional headroom for draining sockets and churn. At 1,000 clients × 60 packets/s × two directions, the forwarding workload is 120,000 logical packets/s; 1,000-byte packets contribute 120 MB/s before outer/IP/link overhead. This is offered load, not achieved throughput. Kernel socket buffers, file descriptors, TLS/QUIC/SCTP state and Rocketnet arenas must all be counted. [R1; arithmetic]

**OPINION topology B, direct native termination:** Embed a browser transport and dispatch decrypted outer messages into a driver that supplies stable virtual source addresses per session. This eliminates the UDP hop/socket-per-client cost but makes identity allocation, worker affinity, lifecycle and driver ownership first-class native work. Connection IDs must not be hashed into a collision-prone port without an allocator. The address fed to Rocketnet is an internal namespace, never an externally spoofable assertion. Decide whether to document this as a transport profile or introduce an opaque endpoint abstraction; do not quietly claim the public address API already supports URLs. [R1, R3, R4]

**SOURCED/OPINION fast path:** The present XDP/GSO interfaces process Rocketnet UDP packets, not QUIC TLS or SCTP. A gateway on another host can forward UDP over a real NIC into the existing server path; that preserves the possibility of its XDP receive path, not the whole end-to-end zero-copy claim. Loopback, veth and overlay deployment need actual attach/routing validation; same-host loopback must not be assumed to traverse physical-NIC AF_XDP. GSO batches UDP toward the server but does not eliminate browser crypto or gateway copies. Direct termination skips that UDP driver path for browser sessions while native UDP clients can retain it. [R4, R5]

**OPINION deployment:** Use a nearby gateway to minimize G and measure receive-to-forward queue delay separately from physical-hop RTT. Shard by session/QUIC connection identity with stickiness; drain rather than move live source ports between machines. On gateway failure obtain a fresh token and reconnect unless a separately specified resume protocol exists. H3 requires UDP-aware ingress with matching WebTransport support; an ordinary TLS-terminating HTTP proxy is not enough. WSS uses ordinary HTTPS names and certificate rotation; RTC authenticates DTLS fingerprints via authenticated signaling, plus authenticated TURN credentials where used. A TURN relay normally forwards DTLS ciphertext, whereas the WebRTC gateway terminates outer DTLS. [S4, S29–S34]

**UNVERIFIED cost ledger:** Added microseconds per hop, CPU/client, packets/s/core, memory/client and connection setup CPU are unknown for every proposed stack. Measure baseline idle RSS, slope across 0/100/1,000/10,000 sessions, kernel memory, handshake churn, context switches, bytes copied, and CPU under each actual cipher. A bulk QUIC throughput graph cannot supply these numbers. [OPINION methodology]

## 3 Protocol mapping

**SOURCED wire baseline:** Token 768 bytes; request 710; cookie 38; challenge 66; response 50 including required padding. Three request/response exchanges precede first keep-alive. Session overhead is 26 bytes plus at least a 7-byte ACK block; sequence is four wire bytes reconstructed to 64 bits, zero invalid; normative replay depth at least 4096. The pure token/key/protocol code uses sodium calls matching the standard, including the four BLAKE2b contexts. The server cookie gate runs before asymmetric work. Keep packet types 0–9 intact for the initial tunnel. [R1, R6–R8]

**OPINION:** Keep inner encryption browser-to-native-server on all three transports for the first design. Outer TLS/DTLS ends at the gateway, inner packet protection ends at the game server. This limits the gateway's intended authority to routing, delaying, dropping and observing lengths/timing, provided it does not receive token secrets or control the browser code/bootstrap trust. This is an architectural intent, not a guarantee against implementation flaws, endpoint compromise or active traffic analysis. [R1, R6, R7]

**Critical token distinction (SOURCED):** The full token includes the two token keys in clear after the 576-byte signed data and 64-byte signature. Do not send that full token to an untrusted gateway as an admission message, cookie, URL, or header. The ordinary request contains signed data and signature, not those clear key copies; the gateway can verify the Ed25519 signature, time, version, protocol and target server without a shared signing secret and without opening the sealed private block. Signature validity is not proof that the sender possesses token keys or a complete account identity: client ID/user data are sealed to the server. Bound provisional allocations and let the server's challenge/response finish admission. A gateway given token keys before handshake can actively impersonate endpoints; forward secrecy of an already completed honest exchange does not justify handing it those keys. [R1, R6, R7]

| Token delivery | Proposed disposition (OPINION), with sourced mechanism |
|---|---|
| HTTPS backend fetch response | Preferred: authenticated game backend supplies token and separate browser endpoint descriptor directly to page memory. Same trust origin as the client code; avoid logging/caches and clear references on disconnect. [R1] |
| URL fragment | Not sent as HTTP request target, but visible to page scripts/history/extensions; avoid full token here. A short one-use bootstrap reference is a separate design. [S6; OPINION] |
| Cookie | HttpOnly cannot be read by the client crypto; readable cookie expands ambient exposure. Full-token gateway cookie conflicts with relay trust. Backend session cookie for token fetch is different. [R6; OPINION] |
| Header | Fetch may use authorization subject to origin policy; WebSocket constructor does not accept arbitrary request headers. Do not smuggle bearer secrets into subprotocol strings. [S6] |
| First WebSocket message | Carry the ordinary Rocketnet request, or only signed routing claims. Never the complete token when gateway confidentiality is the goal. [R6; S6] |

**ESTIMATED byte cost:** For a payload p and minimum ACK, inner size is p+33 (100 bytes becomes 133, an extra 33%; 1,000 becomes 1,033, 3.3%). The 26-byte seal overhead alone is 26% or 2.6%, respectively. A fragment adds another six bytes. Outer QUIC/DTLS/SCTP/TCP/IP costs vary with connection IDs, packet numbers, record packing, ACKs and address family; measure wire bytes, do not add one invented constant. A client WebSocket frame containing 1,033 bytes adds eight framing/masking bytes before TLS/TCP/IP; the corresponding unmasked server frame adds four. At 60 Hz each direction the inner 33-byte overhead alone is 1,980 B/s per direction. Double encryption means two protection passes across different endpoints, not a proven 2× CPU multiplier. [R1; S35]

**OPINION alternative termination profile:** If gateway becomes the trusted game endpoint, it can terminate Rocketnet or replace inner authentication with outer security and backend admission, then use a separate native connection. This changes who holds keys and what server ACKs mean; it is not a byte relay and cannot simply strip 26 bytes from the present packet. A private-network UDP leg still needs its own authentication/confidentiality decision. Only consider this after measured inner-crypto cost justifies a new trust/protocol profile. [R1, R6, R7]

**SOURCED plus OPINION handshake mapping:** Outer address validation proves the browser's path to the gateway. Rocketnet's cookie still validates the gateway UDP source toward the game server; it is not redundant at that boundary. Keep the cookie, challenge, response padding, token replay/admission rules, and counters in a transparent tunnel. In direct trusted termination, skipping a cookie might be justified by validated outer path metadata, but requires an explicit profile with anti-amplification/resource limits and proof-of-key possession; the last handshake exchange is not dispensable just because TLS succeeded. The client schedules sends after transitions rather than replying immediately; at the default 10 Hz this contributes observable connect delay beyond nominal RTT. `CLAUDE.md`'s two-RTT summary is stale relative to STANDARD's three exchanges and the inspected code. [R1, R5, R7, R8]

**OPINION MTU contract:** Await outer readiness, obtain WT maximum D, and require inner packet budget B ≤ D in both directions. A 1232-byte UDP payload wrapped in QUIC does not fit a path that only has 1232 bytes for all QUIC payload and overhead. Set a deliberately conservative initial browser budget such as 1100 only as an experiment; it is not universally safe. The 710-byte request must fit too. A gateway cannot split encrypted Rocketnet packets into native Rocketnet fragments without endpoint cooperation. Choices are: configure both endpoints' budget; define bounded adapter-level reassembly; use a reliable stream only for oversized exceptional traffic under an explicit profile; or reject/fallback. Existing receive ceiling 1426 remains unchanged. Because the server budget is not negotiated on the wire, a browser-only server configuration is the simplest first spike; mixed clients need a specified per-session budget solution. [R1, R3; S1–S3]

**Correction to the brief/standard (SOURCED inference):** 1232 is derived from the IPv6 minimum MTU minus IPv6/UDP headers. It is not a universal promise that IPv4 never fragments, nor does it account for another transport's encapsulation. Smaller IPv4 paths and tunneling require path-MTU handling. Treat the standard's absolute wording as a deployment assumption to revise, while retaining its conservative default for ordinary native paths. [R1; S50, S51]

**OPINION migration:** QUIC connection migration or ICE restart may preserve the outer session; keeping the gateway's UDP socket then hides the browser's changed address from native Rocketnet. This is conditional on browser/stack behavior, stable gateway state and timeout budgets, not guaranteed mobile continuity. WSS reconnect is a new transport session; do not attach it to an old UDP socket based only on a public ID. A resume proof, expiry and replay-safe transfer rule would be new work. Gateway failover remains a different problem from browser network handover. [R1; S29, S33]

**OPINION specification additions:** Add an encapsulation profile describing one inner packet per outer message, trustworthy route descriptor, token-key exclusion, bounded queues, effective MTU, virtual address ownership, congestion/backpressure/drop accounting, transport capability reporting and gateway lifetime. Add separate normative changes before skipping cookies, changing identity to opaque endpoints, negotiating budgets, resuming sessions, or terminating inner protection. Pure ciphertext tunneling with stable real UDP source and unchanged packets needs no wire-format change. Preserve ACK/replay meaning at the native endpoint: a browser write Promise or SCTP ACK is not a Rocketnet game delivery ACK. [R1–R4; S1, S4]

## 4 Client library

**SOURCED code seam:** The public header exposes transport create/update/send/receive and borrowed packet views; driver callbacks are C++ internal operations. `rocketnet_client_transport.cpp` creates its receive thread unconditionally, drains driver packets into bounded buffers, timestamps them, and sleeps 1 ms in that thread. Therefore “compile C++ and add JS socket calls” is incomplete. A browser variant needs either pthread integration or a nonblocking poll/event pump preserving update/buffer lifetimes. The message-layer document describes future object composition; the inspected public header exposes layer-1 message sizing/configuration, so this report does not assume a finished high-level message client. [R2–R5]

| Family | Benefits (OPINION) | Risks and explicit proof |
|---|---|---|
| Existing C++ → WASM, JS transport adapter | Reuse exact wire, ACK, fragmentation, crypto and future message logic; one core for engines. | Port platform time/RNG/thread dependencies; bound JS↔WASM copies; no retaining borrowed frames after native lifetime. Start single-threaded in a Worker, asynchronously collect packets and call update. Verify a no-pthread build actually initializes. [R3–R8; S24–S26] |
| TypeScript wire client + sodium module | Natural Promises/Workers, easier JS packaging and diagnostics; an independent implementation tests the spec. | Reimplement four sequences, 64-bit arithmetic, contexts, replay/ACK windows, fragments, admission and timers. Use BigInt or explicit paired words, never imprecise Number for uint64. TS plus WASM crypto is not necessarily smaller or faster. Keep as a challenger until differential conformance passes. [R1, R6–R8; S27] |

**ESTIMATED size planning envelope, not measured:** WASM core+sodium 150–600 KiB compressed plus 15–60 KiB glue; TS wire/adapter 20–80 KiB compressed plus 100–400 KiB crypto. These ranges are budgeting hypotheses, not outputs of this repository. At 5 Mbit/s, transferring 300 KiB alone costs 300×1024×8/5,000,000 ≈ 0.49 s before RTT, compilation and initialization. Measure raw/gzip/Brotli bytes with exact build flags, cold/warm fetch, streaming compile, first crypto call, first connected packet, and retained heap. Do not include source maps in runtime bytes or subtract the crypto dependency from only one competitor. [OPINION methodology; S26, S27]

**SOURCED crypto fit:** libsodium.js offers WASM and JavaScript variants and wrapper bundles; choose exports by actual required primitives, checking whether sumo is necessary, not by package name. Existing vendored sodium compiled with the client is the lowest-drift candidate. WebCrypto now documents Ed25519/X25519, and compatibility data puts Ed25519 at Chrome 137, Firefox 129, Safari 17; a blanket “browsers lack Ed25519” is outdated. However WebCrypto's standardized algorithms do not provide the complete Rocketnet ChaCha20-Poly1305/BLAKE2b/SipHash/sealed-box stack. AES-GCM substitution would change the wire. Client signature verification is not currently required, so Ed25519 availability alone does not determine feasibility. [R1, R6, R7; S27, S28, S42]

**OPINION memory/threading:** Begin with a fixed WASM arena and bounded incoming/outgoing queues; copy once at API ownership boundaries, then measure. JS typed-array views can be invalidated by WASM memory growth; do not expose long-lived raw pointers to game code. Emscripten pthreads require SharedArrayBuffer and cross-origin isolation (COOP/COEP), complicating third-party embeds, assets and login flows; ship a separate single-threaded build if necessary rather than assuming one binary transparently falls back. Web Workers can separate packet processing from rendering without shared memory; postMessage/copy costs must be included. OffscreenCanvas can move rendering work where supported. AudioWorklet is an audio-processing facility, not a timer loophole or supported networking home. Hidden tabs/mobile suspension must be tested as lifecycle events; neither Worker nor audio promises continuous background play. [S24, S45, S46]

**OPINION engine integration:** Plain canvas consumes Promise-based connect and per-frame delivery batches. Unity WebGL should statically link WASM-compatible native pieces and a `.jslib` transport bridge; the current desktop `librocketnet` dynamic P/Invoke resolver will not simply work there. Blazor can link native WASM dependencies through its documented build system, but its .NET runtime/download/startup cost must be reported separately. Godot web exports can wrap a JS-facing client; threading/export isolation choices should match the game's export mode. Bevy's web examples establish browser WASM deployment, not Rocketnet transport integration; use a Rust/JS boundary or shared WASM bridge and measure copies rather than promising zero-copy across independently managed heaps. [R3; S37–S39, S47]

**OPINION conformance:** Run Appendix A byte-for-byte in browser builds with fixed test inputs; keep production RNG separate. Add native/browser differential transcripts for all packet types, lost cookie/challenge/keep-alive, key-phase separation, zero sequence, 2^32 reconstruction boundary, replay-window edge, fragment reorder/duplication/abandonment, token expiry and malformed lengths. TS must interoperate against the native server in both directions, not merely round-trip its own encoder. Report failing vectors before performance. None of this was executed here. [R1, R6–R8]

## 5 Measurement plan

Everything in this section is an **OPINION proposed harness**, not a result. Tools/protocol mechanisms are sourced where named. The Mac rung is a future browser/native functional demonstration; Linux remains the performance and netem bench. No server was started during this research. [S48, S52]

**Machines and pinned manifest:** Use one Apple Silicon Mac with Chrome, Edge, Firefox and Safari; one Windows x86-64 client; one Linux x86-64 client; a physical midrange Android phone and an iPhone/iPad; a separate bare-metal Linux server and Linux two-interface netem router. Record exact CPU, core count, RAM, OS/kernel/build, NIC/driver/offloads, power mode, thermal state, browser full version, library commit, cipher, certificate mode and transport draft. Use current stable at test start plus the oldest supported build from section 6; exact executable versions are **UNVERIFIED** until the lab records them. Do not derive version numbers from browser marketing names.

**Traffic:** Cross 10/30/60 packets/s with 100/300/600/1000/1200 application bytes, both directions, and a 1000-player mixed workload. Separately sweep inner wire sizes including 710, 1100, 1232 and 1426; a 1200-byte game payload exceeds the 1232 budget once ACK/seal overhead is included and must exercise the specified fragmentation/budget policy. Include bursty frames, independent reliable control, and concurrent asset/download traffic. Count application-generated, accepted, queued, sent, dropped, received, expired, duplicate and native-delivered packets independently. [R1, R2]

**Impairments:** Baseline then netem independent loss 0/1/5/10%, one-way delay 20/50/100 ms (explicitly one-way), jitter ±5/20 ms with recorded distribution, reorder 1/5%, rate limits 128 kbit/s/1/5 Mbit/s, and a burst-loss model with recorded transitions plus deterministic 100/500 ms outages. Apply asymmetric cases and both directions. Record qdisc seed/config, queue limits and placement; host egress artifacts must not masquerade as internet behavior. Exhaustive Cartesian testing is expensive: screen with selected decisive cases, then expand boundary failures. [S48]

**Time and tails:** Browser `performance.now()` is monotonic within its context; it is not a synchronized server clock. Record enqueue, transport send callback, gateway ingress/egress, native receive/update and echo times. Use monotonic native clocks and NIC/kernel timestamps where the host supports them. RTT echo needs no cross-host clock alignment; do not call RTT/2 measured one-way latency. For one-way results calibrate clock offset/drift, preferably with synchronized lab hosts and uncertainty bounds, and reject sub-millisecond comparisons whose uncertainty exceeds the effect. Browser coarsening/event-loop delay is part of the end-user observation. [S52]

**ESTIMATED sample requirement:** 1,000,000 packets per independent cell yields about 10,000 observations beyond p99 and 1,000 beyond p99.9; it does not prove independence. At 60 Hz one flow takes 16,667 s ≈ 4.63 h; at 10 Hz 27.8 h. Use at least five separately seeded runs, report per-run tails plus block-bootstrap intervals, and aggregate only comparable conditions. Initial screening may use 100,000 samples (100 expected beyond p99.9) explicitly labeled preliminary. Concurrent flows save wall time but introduce shared contention and cannot be presented as independent replicas. Count loss/censored late packets alongside latency quantiles to prevent “fast by dropping everything.”

**Setup:** 1,000 fresh connections per browser/network/transport condition, separated into cold DNS/TLS, resumed outer connection, token fetch, signaling/ICE, `ready`/channel-open, Rocketnet first request, native admission, first payload and first render. Capture abandonment, retransmissions, certificate failure and race cancellation. Observe p50/p95/p99, failure rate and deadline overshoot.

**Server and phone:** Sweep sessions 0/100/1,000/10,000 and send rates; measure CPU/core, PPS/core at fixed delivery/tail targets, RSS slope, kernel socket memory, FD counts, per-connection state, allocation rate, handshake churn and retained state after disconnect. Measure Linux gateway/direct/native baselines with equal hardware and offloads. On phones compare 30-minute controlled runs at fixed brightness/render load against network-idle baseline, recording energy with platform tools or external power meter, temperature, battery state, CPU and foreground frame stalls. Battery percentage alone is too coarse for a micro-cost claim.

**Reach:** Real home NAT, double NAT, CGNAT cellular, IPv6-only/NAT64, Wi-Fi↔cellular transition; additionally block UDP, block only QUIC, force TURN UDP/TCP/TLS, insert an authorized TLS-inspection proxy, and disable RTC by managed policy. Label actual network/device/build; “school network” is not one reproducible configuration. Measure success and time-to-fallback, not merely API existence.

**OPINION selection gates, agreed before runs:** First require all conformance cases and bounded memory. For WSS, quantify added p99/p99.9 delay relative to datagrams; label degraded realtime mode if p99 extra delay exceeds 50 ms. If RTC improves reachable target players by ≥2 percentage points or p99 freshness by ≥20 ms without exceeding 2× operating cost, revisit primary transport. These are proposed product thresholds, not sourced universal game requirements. Server capacity passes only at 1,000 real sessions/60 Hz with headroom and no unexplained drops; define acceptable headroom in deployment sizing.

## 7 Ideas of your own

Each entry is an **OPINION idea**, not implemented behavior.

- **Idea — race connectivity, not identities.** Start WT, then WSS after a measured short delay; optionally RTC for cohorts where it improves reach. Finish one Rocketnet handshake on the winner and cancel losers. If racing full handshakes, use separately issued attempts and respect token-admission limits; never accidentally occupy two slots. [R1]
- **Idea — authenticated transport descriptor.** Backend delivers browser URL, allowable native destination, certificate mode and a conservative budget alongside the token. Keep token keys out of gateway-visible metadata. This avoids trying to squeeze URLs into signed IP fields without a version decision. [R1, R6]
- **Idea — capability contract visible to the game.** Expose effective unreliable/reliable path, queue age, MTU and reconnect cause; lower snapshot cadence or switch to interpolation/spectator mode on TCP, rather than silently pretending all transports behave alike. [S1, S6]
- **Idea — stale data cancellation before sealing.** Replace queued snapshots while they are still game messages; avoid generating crypto/ACK state for data already obsolete. Reliable control remains ordered under its own semantics. [R2]
- **Idea — relay admission independent of account identity.** Verify only the signed routing slice, enforce budgets, then trust native proof-of-possession/admission feedback. Public claims do not reveal the sealed client ID. [R6–R8]
- **Idea — certificate service by region.** Use one managed, automated certificate endpoint per gateway region rather than individually maintaining certificates for every transient game server; inner keys remain server-specific. Hash certificates are a controlled lab/deployment option with expiry tests. [S11]
- **Idea — mobile resume research.** Try outer path migration while retaining source-port identity before proposing native-wire migration. Measure outage duration and timeout behavior; a lost gateway still requires a separate recovery design. [R1; S29, S33]
- **Idea — spectator/replay split.** Deliver bulk replay chunks on streams/CDN and timely spectator state on datagrams; explore MoQ only if object subscriptions/fanout justify its added layer. Keep these workloads from inflating the player transport queue. [S1, S36]
- **Idea — browser adversary budget.** Treat tokens as stealable bearer credentials on a compromised page, keep authoritatively validated game state on server, apply backend issuance/rate limits and minimize third-party script authority. WASM opacity is not anti-cheat. This is a threat model proposal, not a guarantee. [R1; OPINION]
- **Idea — rendering contention as a network metric.** Include WebGPU/render-heavy frames and Worker message scheduling in latency tests; an excellent network path can still deliver a late playable frame. [S46; OPINION]
