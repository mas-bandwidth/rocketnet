“Closed” means the named receive path refuses the malformed structure before
the described unsafe read/copy/admission. “Caller bounded” identifies a raw
primitive whose bound belongs to its callers. A successful cryptographic open
does not itself validate the decoded grammar. Kernel-owned completion pointers,
lengths and ancillary headers have the posted-buffer OS contract; they are not
packet bytes an unauthenticated peer may supply directly. None of the parsing
rows allocates storage based on a received length/count. Sessions and message
regions use locally sized, preallocated tables/rings; exhaustion drops, defers
or closes as indicated. The map does not assert that all bounded resource use
or every lifetime interleaving has been model checked.

## 2. Packet and token geometry

All datagrams begin with type 1, epoch 1 and filter 4. The prefilter proves the
whole wire extent is 6..1452 before reading them. Types 9..255 are reserved;
client/server direction gates precede type-indexed counters. Session headers
hold 32-bit sequence after the prefilter, then authenticated plaintext and a
16-byte AEAD tag. Only challenge/denied add an explicit 8-byte nonce. Session
plaintext begins with a 7..1027-byte ACK block; its consumed length determines
the remaining type data.

| Type | Direction | Required wire bytes | Parsed body |
|---|---|---|---|
| 0 request | client to server | exactly 710 | cookie 24, salt 8, ephemeral key 32, signed data 576, signature 64 |
| 1 denied | server to client | exactly 34 | sequence 4, nonce 8, tag 16, no plaintext |
| 2 challenge | server to client | exactly 66 | sequence 4, nonce 8, encrypted ephemeral key 32, tag 16 |
| 3 response | client to server | exactly 50 | sequence 4, encrypted zero padding 24, tag 16 |
| 4 keep-alive | both | 41..1452; type data exactly 8 after ACK | client index 32, max clients 32 |
| 5 payload | both | 34..1452; type data 1..1416 after ACK | message form/records or opaque transport payload |
| 6 disconnect | both | 33..1452; no type data after ACK | ACK block only |
| 7 cookie | server to client | exactly 38 | echoed salt 8, opaque expiry 8+MAC 16 |
| 8 ACK | both | 33..1452; no type data after ACK | ACK block only |

There is no separate packet-fragment parser at this base: legacy type 9 is
reserved. Large messages use authenticated message BLOCK records. Their
fragment index/count are uint16; the count is count-minus-one+1, but the local
1 MiB maximum and fragment size 1152 reduce any admitted block to at most 911
fragments. The message reader checks count, fragment, exact nonfinal size,
last-fragment size, window, ring base/span and final aggregate bound before
delivery. No remote fragment count allocates a new array.

The API token is 768 bytes: signed 576, signature 64, clear keys 32+32, zero 64.
Signed fields occupy 521 bytes and have zero 55. The sealed block at signed
offset 89 has 432 bytes and opens to 384: fields 344, zero 40. The server request
carries only signed data and signature, not the outer clear keys/zero 64. The
server verifies the signature before opening the private block and cross-checks
the private protocol/expiry. F2 records the absent zero-tail validation.

### F1 — Low: client GSO receive stages a truncated completion

**Site:** `sdk/rocketnet_client_gso_linux.cpp:408` in
`rocketnet_client_gso_receive_batch`; carry publication is at lines 445–448.
The receive syscall uses `MSG_DONTWAIT` at line 51, not input `MSG_TRUNC`.
It receives into a 64 KiB buffer, so the returned copied length remains bounded.
However, the output `msg_flags & MSG_TRUNC` is not checked before GRO splitting
and staging. An oversized/coalesced input that yields such a kernel completion
can therefore stage incomplete receive data. A no-GRO oversized view is later
rejected by the common wire ceiling; this audit proves neither an out-of-bounds
read nor an authentication bypass, and does not establish which deployed kernel
or GRO configuration can produce this completion from peer traffic.

**Reduction:** reject a completion marked `MSG_TRUNC` before split/carry/copy,
spend the existing bounded skip budget, and preserve valid complete receives.
Use an existing appropriate drop counter if needed. The server equivalent
already rejects this flag at `sdk/rocketnet_server_gso_linux.cpp:868` and
io_uring rejects it at `sdk/rocketnet_uring_codec.h:171`. No new API, flag,
allocation, rate-limit key or transport is needed.

**Benign invariant:** `test_audit_client_gso_truncation_refuses` uses the existing
receive syscall seam to return one zero-filled, full-capacity completion with
the truncation flag. It asserts zero returned records and no carry. It uses no
socket, live server or packet reproducer. The current implementation violates
the first assertion, so the existing expected-failure registry marks this open
finding. When the reduction lands, remove that marker and retain the invariant.
The test also has ordinary valid split/length counterparts in
`test_audit_coalesced_receive_bounds` and the existing GSO unit cases.

### F2 — Low: token readers omit required zero-tail checks

**Sites:** `sdk/rocketnet_connect_token.cpp:28`, `:55`, `:363`, and `:393`;
admission callers are `sdk/rocketnet_client_protocol.cpp:213` and
`sdk/rocketnet_server_protocol.cpp:338`.
`standard/TRANSPORT.md:79` requires receivers to drop a structure whose
`zero[n]` field is nonzero. The token layouts at lines 747, 768 and 803 define
private zero 40, signed zero 55 and outer zero 64. The readers copy only the
meaningful prefix and discard those tails; no subsequent zero-tail predicate
appears on these admission paths. A holder of a valid token can vary the outer
64 bytes without changing the parsed token or authentication material. A token
issuer can supply noncanonical signed/private tails under otherwise valid
signature/seal. This expands admitted encodings contrary to the format; it
does not give an unauthenticated peer signing/sealing keys, additional array
capacity, an out-of-bounds access or a demonstrated authorization bypass.

**Reduction:** check outer bytes 704..767 at client token admission; check signed
bytes 521..575 before admitting the token/request; after successful private open,
check bytes 344..383 before reading/committing private fields. Reuse fixed-size
zero checks and existing failure/status handling, wipe private staging on
failure, and keep fixed field geometry. No SDK change is made in this layer.
The conditional absent-family address fields are also not canonicalized by the
raw token readers; layer 2 should enforce their specified zero requirement in
the same fixed-format validation gate.

**Benign invariant:** `test_audit_token_zero_padding_refuses` changes one outer
reserved byte in the existing frozen token, calls the client protocol's local
connect entry, clears the temporary state and asserts refusal. It never writes
or sends a request. At this base the connect is accepted, so the assertion is
registered as an expected failure. Signed/private padding omission is source
evidence; no issuer-signed malformed network fixture was constructed. Layer 2
should add fixed-buffer zero predicates and ordinary unit cases for each tail,
including all-zero acceptance, first/last nonzero refusal and private staging
wiping; no live network witness is required.

## 4. Memory and arithmetic — source review

### 4.1 Scope, premises and verdict

The reviewed closure starts at the authenticated message and ACK readers in
section 1, follows their indices, lengths, copies, releases and acknowledgements,
and includes the send structures those acknowledgements retire. The arena's
19 `RN_PART_*` carve-outs are accounted for below. The fixed transport ACK
histories and the transient packet-builder arrays are separate structures.
Configuration/header definitions and the unreliable-ring operations in
`sdk/rocketnet_endpoint.cpp` were read to close those bounds; none was changed.
This is not a second transport/platform inventory or a cryptographic audit.

No out-of-bounds access, use-after-free or remotely exploitable arithmetic
failure was established by this review. MA-1 is a low-severity source-level
counter-width concern with unverified behavioral impact. MA-2 and MA-3 are
low-severity assurance findings: existing models do not prove all of the
current concrete layouts. A source bound, an abstract model, a recorded TLC
result and a newly executed test are different evidence; none substitutes for
the others here.

The arithmetic premises are explicit:

- Geometry is local create-time configuration. `rocketnet_message_validate_config_ex`
  (`sdk/rocketnet_config.cpp:199`) and the field table
  (`sdk/rocketnet_internal.h:591`) bound the window `W`, receive bytes `B`,
  channel count `C`, packet slots `P`, unreliable delivery allowance `Du`,
  sequenced holds `Ru` and receipt slots `Rq`. `W` is a power of two, at least
  64 and at most `2^20`; `B` is a multiple of 16 and at most `2^20`.
  Message bytes cannot exceed `B`. Peer CONFIG fields are compared with this
  configuration by `rn_ordered_take_config` at `sdk/rocketnet_channel.cpp:1412`;
  they do not resize the arena.
- `rn_region_reserve_sizes` (`sdk/rocketnet_allocator.cpp:120`) widens the
  send-rate/resend-time product before multiplication. The configured rate and
  time ceilings keep that product below `2^64`. It refuses a store class whose
  handle index would not fit, `Q >= UINT32_MAX`, or send-span bytes `SR` above
  `UINT32_MAX`. Because the reserve is also bounded by `SR`, and the base send
  queue is at most `2^20`, accepted `Q` is below `2^26`; the `2Q` unreliable
  entry count therefore fits `uint32_t`. Layout products and alignment sums
  use `uint64_t`; the arena plan checks region-count multiplication and
  `SIZE_MAX` before allocation (`sdk/rocketnet_allocator.cpp:1404`).
- Record fields have finite wire widths before arithmetic. The reader proves
  the fixed and optional header extents, then `length <= remaining - header`,
  channel/type bounds, fragment shape and whole-span bounds before publishing
  a record (`sdk/rocketnet_message.cpp:330`). The largest intermediate from
  the 16-bit fragment fields and fixed 1152-byte stride fits signed 32-bit
  arithmetic even before the stricter configured message/window checks.
  Accepted block counts also fit the descriptor's 16-bit fields.
- `rn_region_ring_span_valid` (`sdk/rocketnet_allocator.cpp:1373`) requires
  aligned, nonempty placement and uses `bytes <= B - offset` after proving
  `offset < B`. It proves physical containment. Sender placement and receiver
  ownership/release rules supply stronger non-overlap and lifetime claims;
  containment alone is not that proof.
- Array indices use bounded local slots, masked/modulo sequence positions, or
  validated local descriptor identities. Long-lived logical cursors are not
  uniformly modeled at their full integer width. In particular, the receive
  admission addition is guarded, but the floor advance increments `R`
  (`sdk/rocketnet_window_receive.cpp:105`) and `RNWindowLayout` explicitly
  excludes the `uint64_t` endpoint. No supported-lifetime bound or practical
  exhaustion route is established here. This remains a proof limitation,
  not evidence of a feasible peer-triggered memory error.

### 4.4 Suspected issues and reductions

#### MA-1 — Low: queued-count width does not match accepted queue capacity

**Sites:** `sdk/rocketnet_allocator.h:63` stores four `uint16_t` live queued
counts. `sdk/rocketnet_channel.cpp:1077` sums them for the empty check;
`:1310` and `:1395` increment them, while `:1721` decrements only a positive
count. The locally accepted descriptor capacity can exceed that representation.
No per-channel/per-priority cap tying it to 16 bits was found.

**Input and impact:** local application enqueue/configuration drives the count;
a peer can affect how long backlog remains, but does not directly supply this
array index or counter value. The source permits the bookkeeping count to wrap
and diverge from the linked FIFO. Current dequeue/rejoin decisions also consult
`queue_head`, and ready insertion checks membership, so this review does not
establish memory corruption, lost delivery or a remote denial of service from
the mismatch. Confidence is high in the width mismatch and limited in its
observable consequence. It was not reproduced.

**Reduction:** remove redundant counts if the only required fact is whether
`queue_head` is empty; otherwise represent the accepted capacity explicitly
and check updates. Avoid adding a new configuration knob. The existing
`RNChannelQueuesLayout` counts from zero through its descriptor capacity using
mathematical integers (`:75`, `:196`); it neither pins this finite-width concern
nor supplies a failing result for it. A later authorized repair should establish
count/FIFO correspondence at the chosen width. No new test or model was made.

#### MA-2 — Low assurance gap: current reassembly layout is only partly modeled

**Sites:** collecting and settling anchors at
`sdk/rocketnet_channel.cpp:792`, `:853`, `:884`, reliable collection at
`sdk/rocketnet_channel_reliable.cpp:32`, and sequenced collection at
`sdk/rocketnet_channel_sequenced.cpp:200`; `proofs/tla/RNBlocks.tla:1`
and `proofs/tla/RNHeldOwnership.tla:1` state their abstraction boundaries.

**Input and impact:** authenticated record length, fragment/count, ring
position and ordering fields reach these copies and ownership transitions.
The inspected source checks shape, physical spans, anchor agreement and final
message size. `RNBlocks` uses legal sender-generated records and a tag per
fragment in 16-byte units; it does not execute the actual byte-copy extent or
all final-fragment rounding. `RNHeldOwnership` begins with complete held
entries and excludes the collecting anchor and its settle-time repoint.
`RNChannelTypes` also models abstract two-fragment arrival/completion, explicitly
excluding byte layout. `RNRing` assumes the relevant release/ACK ordering.
Consequently these models do not jointly prove the full current
code-2/code-3/code-4 representation or
all reader-to-copy arithmetic. No failing memory invariant or unsafe copy was
demonstrated. Severity describes missing assurance, not an observed exploit.

**Reduction:** keep proof claims scoped to their stated representations. In a
separately authorized verification task, close the mapping among validated
record fields, descriptor/held-index identity, byte span and completion/release
lifetime before treating the existing placement/ownership results as a complete
layout proof. Existing `RNBlocks` placement and `RNHeldOwnership` release
witnesses cover narrower properties; neither pins the omitted composition.
No new proof input, trace, model or reproduction is included here.

#### MA-3 — Low assurance gap: scheduler model omits transient array layout

**Sites:** `sdk/rocketnet_packet_builder.cpp:188`, `:215`, `:407` and
`sdk/rocketnet_packet_builder.h:38`; `proofs/tla/RNScheduler.tla:25`.

**Input and impact:** local pending records, which are affected indirectly by
peer acknowledgements, become a bounded item list. The current 96-item ceiling
keeps byte-sized bucket counts, offsets, group positions and indices in range;
the internal writer refuses a larger list before planning. Source review
found no overflow at these constants. However, the scheduler model represents
selection by abstract head/boost predicates. Its comment describes the flat
plan as a refinement, without representing the radix passes, bucket prefix
offsets, temporary arrays, group boundaries or rollback positions. The existing
order/starvation witnesses do not establish those physical bounds.

**Reduction:** state the layout proof limit and pin the byte-index ceiling to
the array capacity when separately authorized to change code; a later layout
verification can establish permutation, group-boundary and rollback properties.
No scheduler behavior change, new model or failing witness is claimed here.
