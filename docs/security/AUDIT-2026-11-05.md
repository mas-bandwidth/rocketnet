# Receive surface audit — 2026-11-05

## Executive summary

This audit reviews how the library handles bytes from the remote endpoint:
every receive path, the packet and token geometry, memory and arithmetic on
authenticated data, the connection state machines, and token and key handling.
The detail sections below record the full evidence; this front section is the
consolidated result a reader can act on first.

Fourteen findings were recorded, all low severity. Three are fixed at this
base and eleven remain open. No finding establishes an out-of-bounds access, an
authentication bypass, or a fail-open state transition. The open findings are
secret-lifetime gaps, one fail-closed behaviour window, and assurance gaps
where an existing model does not cover the current concrete layout. Each open
finding names its reduction in its detail section.

| Count | Fixed | Open | Accepted |
| --- | --- | --- | --- |
| Low (14) | 3 | 11 | 0 |

Two status corrections apply to the historical text below. F1 and F2 were
recorded as open at their original audit bases; both reductions have since
landed and are fixed at this base (commits cited in the findings table). The
historical open language in sections 3 and 5 is preserved as the record of
those bases and must not be read as the current status.

This document records no fuzz-coverage section. Fuzz coverage for this audit
was landed on a separate branch and is pending merge; it is not copied here,
and no fuzz result is claimed by this report.

## Method

- **Surface map.** Discovery starts at every direct receive and transport
  completion, then walks the called readers and post-authentication record
  placement. Section 1 lists the reviewed closure function by function, with
  the bound and verdict for each site.
- **Tokens and crypto.** Section 7 reviews the token format and lifetime, key
  and nonce construction, expiry and clock handling, cookie derivation,
  replay and used-once rules, comparison form, key-material erasure, and the
  environment and development-key boundaries.
- **State machines.** Section 6 checks the connection, handshake and session
  transitions, the slot tables, per-connection reset, and the replay window
  against the TLA+ models, including reversed witnesses that reproduce the
  failure each model rules out.
- **Memory and arithmetic.** Section 4 reviews the authenticated readers and
  the structures their indices reach, and records where each layout model
  covers the concrete layout and where it does not. Sanitizer and build
  evidence is recorded in section 4.5 with its scope limits.
- **Fuzz extension.** Before/after fuzz coverage is recorded on the separate
  branch named above; this report makes no fuzz claim.

Case execution is not part of this report: cited test cases and models were
verified to exist, not run. A timeout is not a proof, and no open finding is
called fixed.

## Residual risk

The eleven open findings are the residual risk of this audit. None is an
established memory-safety or authorization failure: TC-1 and TC-4 leave secret
material unwiped on refused paths inside the owning process; TC-3 opens a
post-disconnect rebinding window only after more live bindings than eight
times the client capacity; TC-6 extends an admitted handshake by at most its
deadline, once; TC-5 records an unproven bound that needs on the order of the
full sequence range to matter; S2, S3, MA-1, MA-2 and MA-3 are model-coverage
and counter-width gaps whose source bounds were inspected but not jointly
proved. Each remains open until its reduction lands with its pin; the detail
sections state the confidence and the limits of each.

## Out of scope

- Volumetric floods from many real addresses, answered by deployment and the
  backend rather than this layer.
- Red-team and exploit work, by design; this audit is source review,
  modelling and bounded witnesses.
- Address-prefix limits, by design; admission uses per-source and global
  budgets, not prefix rules.

“Closed” means the named receive path refuses the malformed structure before
the described unsafe read/copy/admission. “Caller bounded” identifies a raw
primitive whose bound belongs to its callers. A successful cryptographic open
does not itself validate the decoded grammar. Kernel-owned completion pointers,
lengths and ancillary headers have the posted-buffer OS contract; they are not
packet bytes an unauthenticated remote endpoint may supply directly. None of the parsing
rows allocates storage based on a received length/count. Sessions and message
regions use locally sized, preallocated tables/rings; exhaustion drops, defers
or closes as indicated. The map does not assert that all bounded resource use
or every lifetime interleaving has been model checked.

## 2. Packet and token geometry

All datagrams begin with type 1, epoch 1 and filter 4. The prefilter proves the
whole wire extent is 6..1452 before reading them. Types 9..255 are reserved;
client/server direction gates precede type-indexed counters. Session headers
hold 32-bit sequence after the prefilter, then authenticated plaintext and a
16-byte AEAD tag. Only challenge/denied add an explicit 8-byte nonce. Session
plaintext begins with a 7..1027-byte ACK block; its consumed length determines
the remaining type data.

| Type | Direction | Required wire bytes | Parsed body |
|---|---|---|---|
| 0 request | client to server | exactly 710 | cookie 24, salt 8, ephemeral key 32, signed data 576, signature 64 |
| 1 denied | server to client | exactly 34 | sequence 4, nonce 8, tag 16, no plaintext |
| 2 challenge | server to client | exactly 66 | sequence 4, nonce 8, encrypted ephemeral key 32, tag 16 |
| 3 response | client to server | exactly 50 | sequence 4, encrypted zero padding 24, tag 16 |
| 4 keep-alive | both | 41..1452; type data exactly 8 after ACK | client index 32, max clients 32 |
| 5 payload | both | 34..1452; type data 1..1416 after ACK | message form/records or opaque transport payload |
| 6 disconnect | both | 33..1452; no type data after ACK | ACK block only |
| 7 cookie | server to client | exactly 38 | echoed salt 8, opaque expiry 8+MAC 16 |
| 8 ACK | both | 33..1452; no type data after ACK | ACK block only |

There is no separate packet-fragment parser at this base: legacy type 9 is
reserved. Large messages use authenticated message BLOCK records. Their
fragment index/count are uint16; the count is count-minus-one+1, but the local
1 MiB maximum and fragment size 1152 reduce any admitted block to at most 911
fragments. The message reader checks count, fragment, exact nonfinal size,
last-fragment size, window, ring base/span and final aggregate bound before
delivery. No remote fragment count allocates a new array.

The API token is 768 bytes: signed 576, signature 64, clear keys 32+32, zero 64.
Signed fields occupy 521 bytes and have zero 55. The sealed block at signed
offset 89 has 432 bytes and opens to 384: fields 344, zero 40. The server request
carries only signed data and signature, not the outer clear keys/zero 64. The
server verifies the signature before opening the private block and cross-checks
the private protocol/expiry. F2 records the absent zero-tail validation.

## 3. Findings for layer 2

Attempt-2 source assessment: **F1 low severity, high confidence in the missing
truncation gate**, but live reachability of the remote endpoint and resulting delivery impact
remain unverified. **F2 low severity, high confidence in the omitted raw-reader
zero-tail validation**, with only format/canonicalization impact established
by this review. Existing bounds and authentication checks do not establish a
memory-safety or authorization failure for either finding. The source sites
and feasible reductions below remain relevant at the delivered head. **Neither
finding was reproduced in attempt 2.** The invariant descriptions and execution

### F1 — Low: client GSO receive stages a truncated completion

**Site:** `sdk/rocketnet_client_gso_linux.cpp:408` in
`rocketnet_client_gso_receive_batch`; carry publication is at lines 445–448.
The receive syscall uses `MSG_DONTWAIT` at line 51, not input `MSG_TRUNC`.
It receives into a 64 KiB buffer, so the returned copied length remains bounded.
However, the output `msg_flags & MSG_TRUNC` is not checked before GRO splitting
and staging. An oversized/coalesced input that yields such a kernel completion
can therefore stage incomplete receive data. A no-GRO oversized view is later
rejected by the common wire ceiling; this audit proves neither an out-of-bounds
read nor an authentication bypass, and does not establish which deployed kernel
or GRO configuration can produce this completion from traffic from the remote endpoint.

**Reduction:** reject a completion marked `MSG_TRUNC` before split/carry/copy,
spend the existing bounded skip budget, and preserve valid complete receives.
Use an existing appropriate drop counter if needed. The server equivalent
already rejects this flag at `sdk/rocketnet_server_gso_linux.cpp:868` and
io_uring rejects it at `sdk/rocketnet_uring_codec.h:171`. No new API, flag,
allocation, rate-limit key or transport is needed.

**Benign invariant:** `test_audit_client_gso_truncation_refuses` uses the existing
receive syscall seam to return one zero-filled, full-capacity completion with
the truncation flag. It asserts zero returned records and no carry. It uses no
socket, live server or packet reproducer. The current implementation violates
the first assertion, so the existing expected-failure registry marks this open
finding. When the reduction lands, remove that marker and retain the invariant.
The test also has ordinary valid split/length counterparts in
`test_audit_coalesced_receive_bounds` and the existing GSO unit cases.

### F2 — Low: token readers omit required zero-tail checks

**Sites:** `sdk/rocketnet_connect_token.cpp:28`, `:55`, `:363`, and `:393`;
admission callers are `sdk/rocketnet_client_protocol.cpp:213` and
`sdk/rocketnet_server_protocol.cpp:338`.
`standard/TRANSPORT.md:79` requires receivers to drop a structure whose
`zero[n]` field is nonzero. The token layouts at lines 747, 768 and 803 define
private zero 40, signed zero 55 and outer zero 64. The readers copy only the
meaningful prefix and discard those tails; no subsequent zero-tail predicate
appears on these admission paths. A holder of a valid token can vary the outer
64 bytes without changing the parsed token or authentication material. A token
issuer can supply noncanonical signed/private tails under otherwise valid
signature/seal. This expands admitted encodings contrary to the format; it
does not give an unauthenticated remote endpoint signing/sealing keys, additional array
capacity, an out-of-bounds access or a demonstrated authorization bypass.

**Reduction:** check outer bytes 704..767 at client token admission; check signed
bytes 521..575 before admitting the token/request; after successful private open,
check bytes 344..383 before reading/committing private fields. Reuse fixed-size
zero checks and existing failure/status handling, wipe private staging on
failure, and keep fixed field geometry. No SDK change is made in this layer.
The conditional absent-family address fields are also not canonicalized by the
raw token readers; layer 2 should enforce their specified zero requirement in
the same fixed-format validation gate.

**Benign invariant:** `test_audit_token_zero_padding_refuses` changes one outer
reserved byte in the existing frozen token, calls the client protocol's local
connect entry, clears the temporary state and asserts refusal. It never writes
or sends a request. At this base the connect is accepted, so the assertion is
registered as an expected failure. Signed/private padding omission is source
evidence; no issuer-signed malformed network fixture was constructed. Layer 2
should add fixed-buffer zero predicates and ordinary unit cases for each tail,
including all-zero acceptance, first/last nonzero refusal and private staging
wiping; no live network witness is required.

## 4. Memory and arithmetic — source review

### 4.1 Scope, premises and verdict

The reviewed closure starts at the authenticated message and ACK readers in
section 1, follows their indices, lengths, copies, releases and acknowledgements,
and includes the send structures those acknowledgements retire. The arena's
19 `RN_PART_*` carve-outs are accounted for below. The fixed transport ACK
histories and the transient packet-builder arrays are separate structures.
Configuration/header definitions and the unreliable-ring operations in
`sdk/rocketnet_endpoint.cpp` were read to close those bounds; none was changed.
This is not a second transport/platform inventory or a cryptographic audit.

No out-of-bounds access, use-after-free or remotely exploitable arithmetic
failure was established by this review. MA-1 is a low-severity source-level
counter-width concern with unverified behavioral impact. MA-2 and MA-3 are
low-severity assurance findings: existing models do not prove all of the
current concrete layouts. A source bound, an abstract model, a recorded TLC
result and a newly executed test are different evidence; none substitutes for
the others here.

The arithmetic premises are explicit:

- Geometry is local create-time configuration. `rocketnet_message_validate_config_ex`
  (`sdk/rocketnet_config.cpp:199`) and the field table
  (`sdk/rocketnet_internal.h:591`) bound the window `W`, receive bytes `B`,
  channel count `C`, packet slots `P`, unreliable delivery allowance `Du`,
  sequenced holds `Ru` and receipt slots `Rq`. `W` is a power of two, at least
  64 and at most `2^20`; `B` is a multiple of 16 and at most `2^20`.
  Message bytes cannot exceed `B`. CONFIG fields from the remote endpoint are compared with this
  configuration by `rn_ordered_take_config` at `sdk/rocketnet_channel.cpp:1412`;
  they do not resize the arena.
- `rn_region_reserve_sizes` (`sdk/rocketnet_allocator.cpp:120`) widens the
  send-rate/resend-time product before multiplication. The configured rate and
  time ceilings keep that product below `2^64`. It refuses a store class whose
  handle index would not fit, `Q >= UINT32_MAX`, or send-span bytes `SR` above
  `UINT32_MAX`. Because the reserve is also bounded by `SR`, and the base send
  queue is at most `2^20`, accepted `Q` is below `2^26`; the `2Q` unreliable
  entry count therefore fits `uint32_t`. Layout products and alignment sums
  use `uint64_t`; the arena plan checks region-count multiplication and
  `SIZE_MAX` before allocation (`sdk/rocketnet_allocator.cpp:1404`).
- Record fields have finite wire widths before arithmetic. The reader proves
  the fixed and optional header extents, then `length <= remaining - header`,
  channel/type bounds, fragment shape and whole-span bounds before publishing
  a record (`sdk/rocketnet_message.cpp:330`). The largest intermediate from
  the 16-bit fragment fields and fixed 1152-byte stride fits signed 32-bit
  arithmetic even before the stricter configured message/window checks.
  Accepted block counts also fit the descriptor's 16-bit fields.
- `rn_region_ring_span_valid` (`sdk/rocketnet_allocator.cpp:1373`) requires
  aligned, nonempty placement and uses `bytes <= B - offset` after proving
  `offset < B`. It proves physical containment. Sender placement and receiver
  ownership/release rules supply stronger non-overlap and lifetime claims;
  containment alone is not that proof.
- Array indices use bounded local slots, masked/modulo sequence positions, or
  validated local descriptor identities. Long-lived logical cursors are not
  uniformly modeled at their full integer width. In particular, the receive
  admission addition is guarded, but the floor advance increments `R`
  (`sdk/rocketnet_window_receive.cpp:105`) and `RNWindowLayout` explicitly
  excludes the `uint64_t` endpoint. No supported-lifetime bound or practical
  exhaustion route is established here. This remains a proof limitation,
  not evidence of a feasible memory error triggered by the remote endpoint.

### 4.4 Suspected issues and reductions

#### MA-1 — Low: queued-count width does not match accepted queue capacity

**Sites:** `sdk/rocketnet_allocator.h:63` stores four `uint16_t` live queued
counts. `sdk/rocketnet_channel.cpp:1077` sums them for the empty check;
`:1310` and `:1395` increment them, while `:1721` decrements only a positive
count. The locally accepted descriptor capacity can exceed that representation.
No per-channel/per-priority cap tying it to 16 bits was found.

**Input and impact:** local application enqueue/configuration drives the count;
the remote endpoint can affect how long backlog remains, but does not directly supply this
array index or counter value. The source permits the bookkeeping count to wrap
and diverge from the linked FIFO. Current dequeue/rejoin decisions also consult
`queue_head`, and ready insertion checks membership, so this review does not
establish memory corruption, lost delivery or a remote denial of service from
the mismatch. Confidence is high in the width mismatch and limited in its
observable consequence. It was not reproduced.

**Reduction:** remove redundant counts if the only required fact is whether
`queue_head` is empty; otherwise represent the accepted capacity explicitly
and check updates. Avoid adding a new configuration knob. The existing
`RNChannelQueuesLayout` counts from zero through its descriptor capacity using
mathematical integers (`:75`, `:196`); it neither pins this finite-width concern
nor supplies a failing result for it. A later authorized repair should establish
count/FIFO correspondence at the chosen width. No new test or model was made.

#### MA-2 — Low assurance gap: current reassembly layout is only partly modeled

**Sites:** collecting and settling anchors at
`sdk/rocketnet_channel.cpp:792`, `:853`, `:884`, reliable collection at
`sdk/rocketnet_channel_reliable.cpp:32`, and sequenced collection at
`sdk/rocketnet_channel_sequenced.cpp:200`; `proofs/tla/RNBlocks.tla:1`
and `proofs/tla/RNHeldOwnership.tla:1` state their abstraction boundaries.

**Input and impact:** authenticated record length, fragment/count, ring
position and ordering fields reach these copies and ownership transitions.
The inspected source checks shape, physical spans, anchor agreement and final
message size. `RNBlocks` uses legal sender-generated records and a tag per
fragment in 16-byte units; it does not execute the actual byte-copy extent or
all final-fragment rounding. `RNHeldOwnership` begins with complete held
entries and excludes the collecting anchor and its settle-time repoint.
`RNChannelTypes` also models abstract two-fragment arrival/completion, explicitly
excluding byte layout. `RNRing` assumes the relevant release/ACK ordering.
Consequently these models do not jointly prove the full current
code-2/code-3/code-4 representation or
all reader-to-copy arithmetic. No failing memory invariant or unsafe copy was
demonstrated. Severity describes missing assurance, not an observed exploit.

**Reduction:** keep proof claims scoped to their stated representations. In a
separately authorized verification task, close the mapping among validated
record fields, descriptor/held-index identity, byte span and completion/release
lifetime before treating the existing placement/ownership results as a complete
layout proof. Existing `RNBlocks` placement and `RNHeldOwnership` release
witnesses cover narrower properties; neither pins the omitted composition.
No new proof input, trace, model or reproduction is included here.

#### MA-3 — Low assurance gap: scheduler model omits transient array layout

**Sites:** `sdk/rocketnet_packet_builder.cpp:188`, `:215`, `:407` and
`sdk/rocketnet_packet_builder.h:38`; `proofs/tla/RNScheduler.tla:25`.

**Input and impact:** local pending records, which are affected indirectly by
acknowledgements from the remote endpoint, become a bounded item list. The current 96-item ceiling
keeps byte-sized bucket counts, offsets, group positions and indices in range;
the internal writer refuses a larger list before planning. Source review
found no overflow at these constants. However, the scheduler model represents
selection by abstract head/boost predicates. Its comment describes the flat
plan as a refinement, without representing the radix passes, bucket prefix
offsets, temporary arrays, group boundaries or rollback positions. The existing
order/starvation witnesses do not establish those physical bounds.

**Reduction:** state the layout proof limit and pin the byte-index ceiling to
the array capacity when separately authorized to change code; a later layout
verification can establish permutation, group-boundary and rollback properties.
No scheduler behavior change, new model or failing witness is claimed here.

### 6.3 Slot tables

`rocketnet_client_slots_t` (`sdk/rocketnet_client_slots.cpp`): the assign pops
the top of a LIFO free stack, refuses a stale owner generation, and writes the
whole user-data record before the slot is readable; release releases only the
exact tenure (client id + generation), erases the open-address index entry with
backward-shift deletion, and pushes the index back once. `rn_slots_t`
(`sdk/rocketnet_slots.cpp`) is the message layer's connection-id table:
`rn_slots_observe` returns NONE/RESET/DROP on the identity change, and
`rn_slots_admit` discards any entry whose connection id is not the bound one.

| Transition | Gate | Effect | Model | Verdict |
|---|---|---|---|---|

### 6.4 Per-connection reset and endpoint reset

`rocketnet_client_connection_reset` wipes secrets with `sodium_memzero`

the ack endpoint; `rocketnet_server_connection_reset` removes the mapping

writes the ending reason, and resets the slot's ack endpoint.
`rn_endpoint_reset` re-carves the region. The RESET/KEEP inventory is
`rocketnet_connection_reset.h` and `docs/CONNECTION-RESET.md`, pinned by
`test_connection_reset_inventory_covers_every_field`.

|---|---|---|---|

### 6.6 Findings (FINDING FORM)

No fail-open transition was found in the audited code: every malformed,
replayed, out-of-order, late, wrong-state or wrong-size packet is refused
before it moves a slot, a mapping, a key or a state, and every disconnect path
resets the per-connection state fail-closed. The three findings below are
model-coverage gaps — transitions the code accepts that the named models do not
carry — and are reported as suspected, unproven by any run of this layer.

**S1 — Low: the standalone ACK (type 8) and, on the server, the payload (type 5)
acceptances are absent from `ClientConnection.tla` / `ServerConnection.tla`.**
Site: `sdk/rocketnet_client_protocol.cpp:1178-1207` (`rocketnet_client_process_ack`)
and `sdk/rocketnet_server_protocol.cpp:1443-1511` (payload/ack delivery). Input:
an authenticated type-8 (or, to the server, type-5) packet. Effect: it refreshes
the idle clock (`last_receive_time`), confirms the slot, and applies its ack
block, so a valid packet of an omitted type keeps a connection alive without
moving its state. What an attacker can do: nothing directly — the packet opens
only under session keys, so an off-path attacker cannot forge one; the omission
is a proof-coverage hole, not a fail-open. Reduction: add `"ack"` (and, in
`ServerConnection`, `"payload"`) to the session packet sets and the
`ClientRecvSession`/`ServerRecvSession` dispatch, as a keep-alive-equivalent
refresh with no state move; pin with a Broken witness that asserts the omitted
type never refreshes the idle clock. `ClientConnection.tla:152` and
`ServerConnection.tla:208` named the omission.

*Closed in the models (attempt 3).* `ClientConnection.tla`: the definition
`ServerAcks` (FALSE; `<- MCServerAcks` only in the new cfgs, so every existing
case keeps its state space) adds `"ack"` to the session types, the server's
`ServerAck`, and the ack arm of `ClientRecvSessionRule` (states 3 and 4, the
session keys, the replay window; the receive clock refreshes, nothing else
moves). Action property `AckNeverMovesState`: an accepted ack leaves the
state, the index and the keys as they were. `ServerConnection.tla`: the
definition `ClientData` (FALSE; `<- MCClientData` only in the new cfgs) adds
the connected client's payload and ack (`ClientSendData`) and their receipt
(`ServerRecvData`: slot gate and keys as a keep-alive, refresh and confirm).
Action property `DataNeverMovesSlot`: a payload or ack creates, establishes,
releases or rebinds no mapping or slot, and touches only a mapping that holds
a slot.

| Case | Spec | Declared | TLC |
|---|---|---|---|
| `MCClientConnectionServerAcks.cfg` | `Spec`, `ServerAcks` on, the committed run's properties plus `AckNeverMovesState` | pass | pass (RUNS.tsv) |
| `MCClientConnectionBrokenAckConnects.cfg` | `SpecAckConnects`: `ClientRecvAckConnects` reads an ack as a keep-alive in state 3 | invariant `ConnectedMeansHandshake` | `Error: Invariant ConnectedMeansHandshake is violated.` |
| `MCServerConnectionClientData.cfg` | `Spec`, `ClientData` on, the committed run's properties plus `DataNeverMovesSlot` | pass | pass (RUNS.tsv) |
| `MCServerConnectionBrokenAckReleases.cfg` | `SpecDataConfused`: the type dispatch reads the ack as a disconnect and releases the slot | action `DataNeverMovesSlot` | `Error: Action property DataNeverMovesSlot is violated.` |

Each counterexample was checked against the code by hand. Client: the trace
loses the first keep-alive ("firstkind"), the server holds the slot and sends
acks, and the witness step connects the client in state 3 without the index;
`rocketnet_client_process_ack` (`sdk/rocketnet_client_protocol.cpp`) runs only
`rocketnet_client_open_session`, which refreshes `last_receive_time` and
never sets `state` or `client_index`, so the code is the passing rule. Server:
the trace connects a client, which sends an ack that the witness step
releases; `rocketnet_server_process_sealed_packet`
(`sdk/rocketnet_server_protocol.cpp`) returns at the ack arm after the
refresh and confirm and reaches the release only for type 6, so the code is
the passing rule. Both groups (`clientconnection`, `serverconnection`) were
rerun in full because their modules changed; RUNS.tsv holds every row.

**S2 — Low: the AEAD integrity-limit teardown transition is absent from the
connection and session models.** Site:
`sdk/rocketnet_client_protocol.cpp:82-93` (`rocketnet_client_integrity_failure`,
state 0) and `sdk/rocketnet_server_protocol.cpp:1142-1173`
(`rocketnet_server_integrity_failure`, slot + mapping removed, reason NONE).
Input: `ROCKETNET_INTEGRITY_LIMIT` (`2^36`, `sdk/rocketnet_constants.h:291`)
sealed packets that fail to open on one connection, across its keys. Effect:
the connection is torn down fail-closed. What an attacker can do: only hasten a
fail-closed teardown of a connection it cannot otherwise enter; it is a defense,
not a weakness. Reduction: add an integrity counter and the teardown transition
to the models at a small limit constant (the production `2^36` cannot be
reached by exhaustive checking), or record the transition as out-of-scope;
`ReplayWindow.tla:204-206` already notes the count is not modelled.

**S3 — Low: the handshake replay window (`handshake_highest_opened`) is
raise-only and is not modelled by `ReplayWindow.tla`.** Site:
`sdk/rocketnet_server_protocol.cpp:1301,1385-1386` (response) and
`sdk/rocketnet_client_protocol.cpp:625,697-698` (challenge/denied), the
reconstruction reference for handshake sequences. Input: a replayed or
far-ahead handshake sequence. Effect: handshake packets are exempt from replay
marking and only raise the high-water mark; the state gates (challenge only in
state 2, denied only in 2/3, response only to an unestablished mapping) prevent
a handshake replay from moving state, so the exemption is not a fail-open, but
the nearest-epoch reconstruction arithmetic for handshake sequences is
unverified by a model. Reduction: extend `ReplayWindow.tla` with a raise-only
handshake window (no mark, high-water advance only) and a witness that a
below-floor handshake sequence is refused, or record the exemption as
out-of-scope. The limitation is stated at `ReplayWindow.tla:44-49`.

Each reduction is a model or documentation change only; no code fix is proposed
because no fail-open transition was identified. If any of these gaps is later
shown to hide a fail-open by a new witness, the fix is surgical and fail-closed,
per the repository's defect-only scope.

### 7.2 Findings

#### TC-1 — Low, OPEN: shared secret not wiped on key-derivation failure

- **Site:** `sdk/rocketnet_keys.cpp:80` in `rocketnet_derive_connection_keys`.
- **Input and effect:** a remote ephemeral public key for which
  `crypto_scalarmult` fails returns 0 at line 81 without the
  `sodium_memzero` of `shared_secret` that the success path performs at
  line 95. No key is derived and both callers refuse the handshake, so
  this is a secret-lifetime gap on a stack buffer, not an authentication
  failure. Confidence is high in the missing wipe; no live impact is
  established and none was reproduced.
- **Reduction:** wipe `shared_secret` before the failure return, matching
  the success path.
- **Pin:** OPEN with the proposed reduction. The only input that reaches
  the failure is a degenerate ephemeral key, which is a crafted-input
  case outside this report-only scope; no benign normal-use case can pin
  the wipe, so no fix is landed here.

#### TC-2 — Low, OPEN: cookie zero-field check is not a constant-time form

- **Site:** `sdk/rocketnet_server_protocol.cpp:579`,
  `memcmp( return_cookie, zero_field, ROCKETNET_COOKIE_FIELD_BYTES )`.
- **Input and effect:** the compared value is the sender's own cookie
  field against a zero constant, so no secret is at risk and the MAC
  comparisons themselves are `sodium_memcmp` (above). This is recorded
  only because the audit item asks for every cookie comparison to take a
  constant-time form; `memcmp` may exit at the first nonzero byte of a
  value the sender supplied.
- **Reduction:** use `sodium_is_zero( return_cookie, ROCKETNET_COOKIE_FIELD_BYTES )`
  for the all-zero test, leaving the gate order and counters unchanged.
- **Pin:** OPEN with the proposed reduction. The change is
  behaviour-preserving, so a benign first-contact case (zero cookie,
  cookie packet issued) passes before and after and cannot pin it; no
  timing measurement is in scope.

#### TC-3 — Low, OPEN: a live used-token binding can be evicted before expiry

- **Sites:** `sdk/rocketnet_token_tables.cpp:342` (binding slot selection)
  and `:490` (record); capacity is `8 × max_clients` bindings
  (`sdk/rocketnet_server_transport.cpp:2203`, outside the change paths).
- **Input and effect:** when the binding table is full and no entry is
  expired, record evicts the oldest live binding, although the table's
  contract states a binding lives until the token expires
  (`sdk/rocketnet_token_tables.h:17`). After eviction and after the
  original connection closes, the same token can be bound from a second
  address inside its expiry. Reaching this needs more distinct bound
  tokens than eight times the client capacity inside their lifetimes,
  and the one-live-connection rule still holds throughout. Confidence is
  high in the eviction behaviour; consequence is limited to the
  post-disconnect rebinding window.
- **Reduction:** make recording fail closed when no expired or free slot
  exists, and refuse the connection response in that case instead of
  connecting unbound; that is a behaviour change in the response path,
  so it is not landed by this report.
- **Pin:** OPEN with the proposed reduction. Existing history cases stay
  as they are; a pin belongs with the authorised behaviour change.

#### TC-4 — Low, OPEN: oversized secret env value leaves its staging unwiped

- **Site:** `sdk/rocketnet_config.cpp:726` in `rocketnet_config_apply_env`.
- **Input and effect:** when an environment value is too long
  (`found < 0`), the function returns at line 729 without the
  `sodium_memzero( value, … )` that the normal path performs at line 739.
  The staging can hold a truncated copy of an operator-supplied secret
  value on the stack of a refused create. No value is logged or used on
  this path. Confidence is high in the missed wipe; exposure is limited
  to the creating process's own stack.
- **Reduction:** wipe `value` before the too-long return, as every other
  exit from the loop does.
- **Pin:** OPEN with the proposed reduction. The staging is not exposed
  through the existing decode-staging hook, so no benign case can
  observe the wipe without a new seam; no seam is added here.

#### TC-5 — Low, OPEN (unproven bound): no enforced packet bound per session key

- **Sites:** nonce construction at `sdk/rocketnet_protocol.cpp:140` and
  sequence allocation at `sdk/rocketnet_protocol.cpp:127`.
- **Input and effect:** (key, nonce) uniqueness rests on the 64-bit
  sequence never repeating under one connection's keys. The allocator
  refuses zero but no bound stops a sequence from reaching the top of
  its range, and no per-connection packet limit or rekey exists; the
  integrity limit bounds failed opens, not valid traffic. At any
  feasible packet rate this needs on the order of 2^64 packets, so no
  practical reuse is claimed — the finding is that the bound is unproven
  and unenforced, not that reuse is reachable.
- **Reduction:** a specification-level decision: cap packets per session
  key well below the sequence range and end the connection at the cap,
  or state the 2^64 bound as accepted. No code change is proposed here.
- **Pin:** OPEN. The existing replay and sequence models pin window and
  reconstruction behaviour at reduced widths; none pins a full-width
  per-key packet bound.

#### TC-6 — Low, OPEN: a response can connect after the token has expired

- **Site:** `sdk/rocketnet_server_protocol.cpp:1014` in
  `rocketnet_server_process_connection_response`.
- **Input and effect:** expiry is checked on the connection request
  (`:475`), not on the response. A response that opens after the token's
  expire timestamp still takes a client slot; only the used-token
  binding is skipped (`:1014`). The window is bounded by the handshake
  deadline of the half-open mapping (default 5 s), after which the
  mapping is swept, and the client's own lifetime deadline runs in
  parallel. Confidence is high in the behaviour; it extends a token's
  usable life by at most that deadline, once, for a handshake already
  admitted.
- **Reduction:** refuse the response when the mapping's
  `token_expire_timestamp` is not later than the current timestamp,
  counting it with the existing token-expired reason; this changes
  admitted-handshake behaviour, so it needs a specification decision
  and is not landed here.
- **Pin:** OPEN with the proposed reduction; no case was written under
  the report-only scope.

### 8.3 Gap findings (FINDING FORM)

Each finding names the site, the input the remote endpoint controls, the
severity, and a suggested harness extension in words. No seed file is
described byte for byte and none was made.

**FUZZ-GAP-1 — Low: no fuzz target reaches the fixed truncated-completion
gate in the client GSO receive.** Site:
`sdk/rocketnet_client_gso_linux.cpp:346` (`rocketnet_client_gso_receive_batch`,
gate at `:420`), with carry delivery at `:324`. Input: a kernel completion
for an oversized or coalesced datagram whose output flags mark the payload
truncated; the bytes themselves arrive from the remote endpoint, but the
truncation mark is produced by the kernel. No existing target can present
it: the pair targets use the loopback transport with no sockets
(`tests/fuzz/rocketnet_fuzz_pair.h:54`), the structured target drives the
protocol layer through the in-repo simulator
(`tests/fuzz/rocketnet_fuzz_receive_structured.cpp:353`), and no harness
names the GSO receive or its syscall seam. Severity low, matching F1: the
gate now drops the completion whole, and the unfuzzed remainder is
confidence in that drop, not a shown overrun. Suggested extension: a new
target `rocketnet_fuzz_client_gso` driving the GSO receive through its
existing syscall seam, with inputs that choose completion length, segment
stride and the truncation and control-truncation flags, and an oracle that
a truncated completion yields no record and no carry while a complete
completion still splits. Seed structure in words: one complete coalesced
message, one truncated message of the same shape, and one of each at the
skip-budget boundary.

**FUZZ-GAP-2 — Low: no fuzz target reaches the platform batch and single
receives.** Sites: `sdk/rocketnet_platform.cpp:2080`, `:2414`, `:4782`,
`:4173` and `:4280`. Input: datagram lengths, sources and kernel
completion counts for real socket receives; the remote endpoint controls
datagram size and source, the kernel controls the completion. All eleven
targets either call a parser directly, use the simulator, or use the
loopback pair, so the true-length preservation, compaction and stride
arithmetic in these five functions never execute under fuzz-chosen
lengths. Severity low: section 1 found the arithmetic bounded under the
caller and kernel contracts, with no runtime reproduction. Suggested
extension: a new target `rocketnet_fuzz_platform_receive` driving each
receive through a fake completion seam, with inputs that choose result
count, per-datagram true length, copied length and source family, and an
oracle that a stored length is never shortened, an oversize datagram
stays visible to the prefilter, and no output slot outside the caller's
batch is written. Seed structure in words: an empty batch, a single
fitting datagram, a single oversize datagram, and a full batch mixing
fitting, empty and oversize entries.

**FUZZ-GAP-3 — Low: no fuzz input can put the MA-1 queued count at its
width.** Site: `sdk/rocketnet_allocator.h:63` (four counts of 16 bits),
incremented at `sdk/rocketnet_channel.cpp:1310` and `:1395`. Input: only
indirect; the remote endpoint can hold backlog open with its
acknowledgements, but the queued count itself is written by local sends.
The session target does execute the increments, through
`tests/fuzz/rocketnet_fuzz_session.cpp:133`, yet its fixed channel count
and bounded script queue only a few messages per run, so the divergence
between the count and the linked list at the width boundary is never
exercised. Severity low, matching MA-1: no memory error, lost delivery or
denial of service was established from the mismatch. Suggested extension:
extend `rocketnet_fuzz_session` with a queue-depth mode whose inputs
choose sustained sends on one channel and priority without receives, or
add a dedicated target `rocketnet_fuzz_channel_queue` that drives the
send queue directly; the oracle in either case is that the queued count
and the linked list agree, including across the width boundary. Seed
structure in words: an empty queue, a single queued message, a queue held
just below the width, and a queue driven across it.

**FUZZ-GAP-4 — Low: the token text wrapper is unfuzzed; only the decoder
beneath it is reached.** Site: `sdk/rocketnet_api.cpp:1275`
(`rn_connect_token_decode`: bounded search for the terminator, exactly
1024 characters, exactly 768 decoded bytes). Input: caller-supplied token
text; at this boundary the caller is the application, and the text
normally arrives from the backend that minted the token. `rocketnet_fuzz`
reaches `rocketnet_base64_decode_data` at `tests/fuzz/rocketnet_fuzz.cpp:266`,
but no harness calls the wrapper, so its length and terminator gates have
no fuzz coverage. Severity low: section 1 found the wrapper closed on
wrong length and alphabet, and the decoder beneath it is covered.
Suggested extension: extend `rocketnet_fuzz` with a fourth selector arm
that feeds the input as token text to the wrapper, with an oracle that
acceptance implies exactly 1024 characters and exactly 768 bytes and
that the decoded bytes equal a direct decode of the same text. Seed
structure in words: a valid encoded token, the same text shortened by
one character, the same text with its terminator moved, and a text whose
decoding is one byte short.
